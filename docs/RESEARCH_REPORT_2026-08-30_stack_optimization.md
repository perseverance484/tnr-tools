## W1. Doctrine lives in four places and drifts

**RQ1 (single-source with generated projections + stdlib diff in CI).** The proven pattern is *spec-as-source with generated projections*: one canonical doc is the source of truth and every other surface is a rendered artifact checked in CI. Netflix's Unified Data Architecture treats the domain model as spec and generates GraphQL/Iceberg/Data-Mesh projections; Stripe maintains a versioned OpenAPI spec from which SDKs and docs are generated. The tradeoff (per Augment Code's writeup) is "near-zero drift risk by construction, but high organizational friction and harder debugging because generated code is harder to trace." For this stack, canonical `docs/00_INDEX.md` (+ a small `docs/DOCTRINE.yml`) is the source; a stdlib `render_doctrine.py` emits (a) the mounted-instructions paste block and (b) each SKILL.md preamble. CI diff is trivial in stdlib: re-render into a temp file and `difflib.unified_diff` against the committed projection, exit 1 on any delta — the same fail-closed shape `skillpack.yml` already uses. This clears all gates (stdlib, Actions/node optional, no writes).

**RQ2 (checksum/version pinning inside mounted-instruction text).** Prior art is the "generated header stamp" pattern used by docs-as-code toolchains and already present in this repo's own generated files (45c/45e/45f carry provenance stamps; the panel shows a cfg-generated stamp). Concretely: emit a first line `<!-- projection of docs/00_INDEX.md@<sha7> rendered <ISO8601> -->` into the paste. Turn-one staleness detection then costs ~1 line to read and a single `git rev-parse` / contents-API call to compare — near-zero tokens. The limitation the brief already names holds: mounted instructions and userMemories cannot fetch at load, so this detects staleness but still needs a human paste to fix it. This is the honest ceiling — pin + detect, not auto-heal.

**RQ3 (extend lawmap's cite-audit to doctrine claims).** Yes, and the precedent is ESLint's `meta.docs.url` convention plus `eslint-plugin-eslint-plugin`'s `require-meta-docs-url` rule, which mechanically enforces that every rule carries a resolvable documentation pointer. Mapped onto doctrine: give each assertion a grep-able id (e.g. `[[D-hidden-true]]`, `[[D-build-order]]`) in the canonical doc, and have `lawmap.py` (or a sibling `doctrinemap.py`) assert each id appears exactly once as a definition and that cross-references resolve. This audits agreement without turning prose into a schema — it only requires stable ids, exactly as lawmap already does for the 93 laws (93 laws, 70 code citations, 5 warnings this session). Recommendation: adopt ids + projection render; effort low, impact high (kills the ~6 K duplicate-doctrine token floor and the "stale copy wins" accuracy failure).

## W2. Session lifecycle is expensive and hand-carried

**RQ1 (handoff schema that survives compaction; proven minimum field set).** The strongest prior art is the arXiv paper *ESAA-Conversational: An Event-Sourced Memory Layer* (2606.23752), which prescribes a split: `handoff.md` (entry contract), `state.md`, `decisions.md`, `tasks.json`, with the rule "turns = evidence; decisions = durable knowledge; tasks = operational continuity; handoff = operational entry point." Its central finding is that a cold agent should begin from these compact views, *not* the full activity log. Complementary and quantified: Factory.ai's own compression evaluation, run over "over 36,000 production messages," found its structured/anchored summarization "scored 3.70 overall compared to 3.44 for Anthropic and 3.35 for OpenAI" — i.e. a persistent structured document extended per eviction beats regeneration from scratch. The convergent proven-minimum field set: fixed schema of **files/records touched, decisions + rationale, in-progress state, constraints/preferences, next steps, and open items by owner**. Verdict for this stack: a *single generated digest* projected into both `status.json` and `active-context.md` beats the current two independently hand-maintained files (which the brief confirms restate each other's state line, blocked list and rulings). This removes the drift class directly.

**RQ2 (session_open.py / session_close.py that emit + verify one digest, <500 tokens).** The write-before-compaction pattern (mem0.ai: "extract after every significant step, before compaction fires") is the design. `session_close.py`: assemble the digest from a small template, write status.json + active-context.md as *projections* of it, then **read them back and assert byte-equality** — directly fixing the `0dca30d` no-op `cp` incident where a close-out from an unmounted path silently failed and only a manual read-back caught it. `session_open.py`: clone, read the digest, run the verify re-runs, print the state line. This lands the archived ROLLOUT_PLAN Stage 4 `session_open.py` proposal that "landed as prose ritual, not script." All stdlib, round-trips through git, stays phone-readable (JSON + short md). Output-token target <500 is met because the human-readable emission is one digest, not a re-narration.

**RQ3 (shallow/sparse clone worth it at 6.3 MB?).** No — clone cost is noise against doctrine-read cost here. The GitHub engineering blog's own guidance is that partial/shallow clones pay off on "extremely large monorepo" scale; at 4.0 MB work + 2.3 MB .git the transfer is seconds. Worse, `--depth 1` shallow clones break `git blame`/history that the audit workflows rely on, and sparse-checkout is cone-mode fiddly on a solo phone-driven repo. The real ~10 K turn-one cost is doctrine *reads*, which W1 (dedupe) and W11 (section addressing) attack. Recommendation: skip clone optimization; build the `session_open/close` pair. Effort medium, impact high (direct ~10 K-token/session + continuity-fidelity win).

## W3. Schema regen is blocked and staleness is invisible

**RQ1 (cheapest reliable upstream-drift sentinel).** The canonical pattern is a scheduled Action that reproduces state and opens/updates a single tracking issue on change — exactly the Terraform drift-detection idiom (cloudposse `github-action-atmos-terraform-drift-detection`: "create or update github issue once drift is detected," run on `schedule:`; and the rosesecurity/Firefly writeups that "close previous drift reports when resolved"). Applied here: a cron Action clones `studie-tech/TheNinjaRPG`, runs `schema_extract.py`, and commits `DRIFT.md` / opens one issue when the extracted hash changes. **Cost/failure bounds to design around:** GitHub's own docs warn scheduled workflows "may be delayed during periods of high load"; community reports (discussion #156282, #196910) document 15-min to multi-hour drift, and low-activity/free-tier repos are scheduled less aggressively. Mitigations from that same corpus: schedule off the top of the hour (e.g. `:17`), add `workflow_dispatch` for manual runs, and treat the sentinel as eventually-consistent (freshness in hours, not minutes) — acceptable because game pushes stay manual regardless.

**RQ2 (Workflows-RW PAT risk vs one-time web-UI upload).** The web-UI route should simply have been taken, and there is no good reason it wasn't. GitHub's constraint (confirmed across community discussions #26254, #35410, and GitHub docs) is that pushing/modifying files under `.github/workflows/` requires the **`workflow` scope** (classic) or Workflows: read-write (fine-grained) — `contents` alone is refused with "refusing to allow a Personal Access Token to create or update workflow." But that scope is only needed to *write the workflow file itself*. Uploading `regen_schemas.yml` once through the GitHub web UI (or committing via the browser, which uses your session, not the PAT) sidesteps it entirely; thereafter `contents: read/write` suffices to edit everything the workflow *does*. Granting Workflows-RW to a long-lived, plaintext-pasted PAT (see W10) needlessly widens blast radius — a leaked token could rewrite CI to exfiltrate. Verdict: **do the one-time web-UI upload; never add Workflows-RW to the container PAT.** Effort near-zero, unblocks the top failure source.

**RQ3 (diff at extracted-artifact level vs upstream-file level).** Diff at the 45x *output* hash, not upstream source files. This is the buf/oasdiff philosophy — detect breakage at the contract layer, not the source layer — and it means upstream churn that doesn't change contracts (refactors, comments, formatting) stays silent, eliminating false-alarm fatigue on a solo maintainer. It also composes with W4's structural gate: the sentinel says "contract changed," W4 says "and here is exactly which key/enum/union changed, fail-closed on removals."

## W4. Extractor adoption has no mechanical gate

**RQ1 (minimal structural-diff gate for JSON contracts; mappable prior art).** The rules map directly onto **buf breaking-change categories** and **oasdiff**. buf's model (buf.build/docs/breaking): adding a field is safe; removing/renaming or changing type is breaking; its FILE/PACKAGE/WIRE categories are a strictness ladder. oasdiff provides "Breaking Change Detection: Automatically identifies changes that break integrations, such as removing a required field, changing a parameter type, or deleting an endpoint" (it detects over 300 breaking-change kinds, categorized ERR = definite vs WARN = potential). The npm `json-schema-diff-validator` is the closest drop-in shape: it fails on breaking changes and exposes exactly the toggles this gate needs — `allowNewEnumValues` (default false), `allowNewOneOf` (default false), `allowReorder` (default false) — i.e. **fail-closed on enum-member removal, union-arity shrink, and required-key removal; allow additive changes.** The SECTOR_TYPES corruption (a global/local enum name collision that silently swapped a union's members) is precisely an enum-member delta with unchanged arity — so the gate must compare enum member *sets by value*, not just counts. All implementable in stdlib (`json` + set algebra); output is a phone-readable added/removed list, exactly like `json-schema-diff`'s "ADDITIONS/REMOVALS" report.

**RQ2 (extractor invariants worth property-testing).** Three, all stdlib-checkable, that make the extractor fail loudly instead of emitting plausible wrongness: (1) **every discriminator literal is unique within its union** — this is the specific invariant that would have caught SECTOR_TYPES; it mirrors buf's enforcement that enum values not collide. (2) **every `$ref`/cross-reference resolves** — the OpenAPI-diff community explicitly flags unresolved `$ref` as a silent-divergence source (ArrayDiff: "if one spec inlines a schema while the other uses `$ref`, they'll appear different"). (3) **enum members are emitted sorted-stable** so diffs are order-independent and reviewable (json-schema-diff-validator's `allowReorder:false` exists precisely because reordering otherwise reads as change). Recommendation: add both the diff gate and the invariant selftest to the `--ctors`-first adoption flow; effort medium, impact high (closes the worst-case *silent* accuracy failure where a wrong enum ships into both validate.py and the builder).

## W5. 23 of 93 laws are enforced only by prose

**RQ1 (smallest simulator-assertion harness for laws 9–13, as a validate.py mode).** Build it as `validate.py --laws` (a mode, not a new tool), reading `45e` constants as the fixture. Each law becomes a red/green property assertion: multiplicative bucket stacking (law 9) → assert combined multiplier equals product of bucket multipliers within float epsilon; same-type product formula (10) → assert same-type stack uses the product rule not additive; pierce bypassing the floor (11) → assert a pierce input drives result below the normal floor; cast-round suppression (12/13) → assert suppressed rounds contribute zero. This is the "executable spec" pattern (spec-drift's "lying test" detection: a test that asserts `200` when it should assert `403` is the failure mode to avoid — so each assertion must check the *value*, not merely that calc.py ran). 12b's own Phase-3 section already names 9–13 as "most worth turning into a simulator assertion," so this lands existing intent. `calc.py`/`sim_damage.py` exist but "assert nothing law-shaped" — this mode gives them assertions.

**RQ2 (marginal cost curve of widening 45g; lazy-load per entity type).** 45g is 21 KB / 18 check entries today; it is script-read by validate.py (no context cost) but *also* shipped to the browser preflight. The Android-Firefox bite is bundle parse/latency, not tokens. The known-good pattern is **lazy-loading checks per entity type**: the userscript already resolves `@require`/resource dependencies via a pathMap (ViolentMonkey `buildPathMap`/`fetchResources`), so loading only the check-shard for the entity being built (jutsu vs AI vs item) is idiomatic and keeps preflight fast. Budget rule: keep the always-loaded core small; shard the long tail. There is no hard published size cliff — treat it empirically (measure panel-open latency on the Samsung device as entries grow), but sharding removes the question.

**RQ3 (prior art on enforcement-provenance tables).** Yes — copy the ESLint `meta.docs.url` + `require-meta-docs-url` model wholesale for the 12b matrix: every rule row carries a machine-checked pointer to its enforcing site, and a lint rule fails if the pointer is missing or wrong (typescript-eslint auto-generates its rule docs from `meta` to keep the table honest). This is exactly the fix for the 5 untrustworthy rows (16d/37/69 claim enforcement with no site; 18/61 enforced but classed knowledge): make the "enforcing site" column CI-verified by lawmap, so a claimed-enforced law with no resolvable citation fails the build. Effort medium; impact high on accuracy tail (knowledge laws fail exactly under late-session context pressure).

## W6. Writes are verified by courtesy, not by construction

**Grounding (subagent-confirmed against the game source).** TheNinjaRPG's developer contract (`.openhands_instructions`, repo root) states verbatim: mutations "set the output to `baseServerResponse` from `@/server/api/trpc`" [github](https://github.com/studie-tech/TheNinjaRPG/blob/main/.openhands_instructions) and "Never use direct database transactions, instead use guards with where-statements and check return results," [github](https://github.com/studie-tech/TheNinjaRPG/blob/main/.openhands_instructions) with mutations structured "queries→guards→mutation." [github](https://github.com/studie-tech/TheNinjaRPG/blob/main/.openhands_instructions) Because the mutation output is a *fixed envelope* (success/message shape), not the per-entity record, **the created/edited row is not returned to the client** — a separate `.get` read-back is architecturally required to know landed state. (Caveat: the exact field list of `baseServerResponse` and whether it carries a generic `data` field could not be quoted from `trpc.ts` directly; the envelope-not-record conclusion follows from the documented "output to `baseServerResponse`" rule, which is a fixed shape rather than a per-entity schema.) This upgrades W6's read-back from "nice to have" to "the only way to close the loop," and it is a *read*, so it stays inside the manual-write doctrine.

**RQ1 (builder auto-appends a read-back after every write; cost).** Prior art for the mechanism is the Attio MCP server's field-verification mode (`ENABLE_FIELD_VERIFICATION`, `STRICT_FIELD_VALIDATION`): after a 200/204 it re-reads and warns/errs on "field persistence mismatch," explicitly to catch APIs that "normalize or reformat your data." Cost analysis for this stack: read-backs are `<entity>.get` tRPC calls issued by the builder that already holds the session token; they add one GET per write entry to the results bundle. Bundle size grows by roughly one canonicalized record per entry (the 52 KB live bundle already carries a per-entry checks inventory, so the format exists). Run-time on mobile: sequential GETs are the dominant cost — batch them after all writes, not interleaved. Rate-limit exposure is negligible against the game API since these ride the same authenticated session as writes and reads are cheap; they do **not** touch GitHub's unauthenticated bucket. Verdict: adopt auto read-back into the bundle; it is the single highest-value change (shortlist #1) and clears every gate (reads are not writes).

**RQ2 (diff granularity that catches the silent classes with fewest false alarms).** Use a **per-manifest "fields I asserted" checklist**, not a full-record canonicalized diff. Rationale from the failure literature: the DEV "How APIs Fail When Agents Use Them" guide and Zendesk's own docs show servers legitimately reshape data (Zendesk strips restricted keys and *sometimes* signals via `X-Zendesk-Api-Warn`; Attio returns `{stage:{title,id,...}}` when you sent `{stage:"Demo"}`). A full-record diff drowns in these cosmetic reshapes (false alarms); asserting only the fields the manifest *claimed to set* catches exactly the three known silent classes — stripped field (asserted field absent), dropped reference (asserted ref id not resolved on read-back), blanked field on partial edit (asserted value now empty) — with minimal noise. (Note: the game's zod input schemas were not directly readable, so whether unknown fields are stripped silently or rejected is unconfirmed; plain `z.object` strips by default, which is the conservative assumption the checklist is designed for.)

**RQ3 (standing verification: scheduled capture of recently-touched ids).** Sound and in-doctrine, because reads are not writes. Pattern: a scheduled Action (same drift-sentinel idiom as W3) or a builder "capture recently-touched ids" action whose results auto-commit to `harvests/inbox/` exactly like normal harvests. This is the "standing verification" analogue of API content-validation monitoring (Hyperping/Domain-Monitor: don't trust 200, re-read the body on a schedule). Constraint honored: it issues only reads, so it needs no human write-tap, and it feeds the same answers-regen pipeline.

## W7. The builder distribution chain trusts a 5-minute-stale CDN

**RQ1 (bundle self-verifies its blob SHA at load).** Feasible and cheap. The browser side already reaches `api.github.com` (the sync uses it), and per GitHub docs "the primary rate limit for unauthenticated requests is 60 requests per hour… associated with the originating IP address" — ample for a per-load check. Pattern: on panel init, fetch the bundle's own blob SHA via the contents API and compare to a SHA the bundle was built with; on mismatch, warn in the panel title (extending the existing panel-title-as-load-check doctrine). **Failure modes to handle:** offline / rate-limited (fail *open* with a "could not verify" note, never block the panel), and the 60/h IP budget shared with the existing sync (cache the check result per session). This turns the human blob-view ritual into an automatic warning.

**RQ2 (commit-pinned jsDelivr under ViolentMonkey `@require` on Firefox Android).** This is the outright fix for the staleness *class*. jsDelivr supports commit-pinned URLs `cdn.jsdelivr.net/gh/user/repo@<sha>/file`, and its own README states the caching tiers explicitly: **"Static Versions and commit hashes — Effectively forever"** (permanently S3-cached, 1-year headers, immutable — "new commit = new URL"), versus **"Version aliasing — 7 days. This also includes latest versions,"** and **"Branches — 12 hours."** `@require` fetches any static URL, so a **loader rewritten per release by a workflow to pin the new commit SHA** eliminates raw-CDN staleness entirely — the loader always points at an immutable URL, so there is no "fresh `?v` still serves stale bytes" failure. This is strictly better than the current raw.githubusercontent `~5-min` cache. Caveat to flag: this depends on jsDelivr (an external CDN) and on a workflow rewriting the loader on each release; the ViolentMonkey `@require` cache itself is sticky (documented in violentmonkey issues #2097/#2162 — required scripts "never get updated" without a manual refresh), so a version bump still needs the ViolentMonkey update, but the *bytes* are guaranteed correct once fetched. Note also: TheNinjaRPG source is "released with no license… exclusive copyright" — jsDelivr serves only *your* `tnr-tools` repo (your code), which is fine; do not route game source through it.

**RQ3 (keep the doc honest — stamp live version into pipeline.md).** Yes: have `skillpack.yml` write a generated header into pipeline.md carrying the live builder version, so the v4.12-vs-v4.27 prose-drift class becomes impossible. This is the same generated-header pattern as W1-RQ2 and the repo's existing provenance stamps. Effort low; the doc can no longer lie about the version. Recommendation for W7 overall: ship self-verify (RQ1) now as the low-risk win; pilot commit-pinned jsDelivr (RQ2) as the class-killer; auto-stamp the doc (RQ3).

## W8. The push loop is ~5 taps that only dauntless can spend

**RQ1 (multi-manifest Build: ordering, isolation, resume; minimal userscript UI).** Batch-replay prior art converges on four requirements (Spring Batch, Airflow, Cloud Run Jobs, oneuptime's batch-retry guide): **idempotent writers** (so a re-run is safe — "restart produces duplicates" without it), **checkpoint/resume from last committed unit** (Spring Batch "resumes from the last committed chunk instead of the last read row"), **failure isolation** (one bad manifest does not abort the batch — Cloud Run Jobs retry per-task index; the batch is declared complete on a fault-tolerance threshold), and a **combined result bundle**. Minimal userscript UI honoring the gates: a multi-select checklist of `push/N` files, **one** confirmation tap (preserving one human tap per *write batch*, as doctrine requires), sequential run with per-entry success/fail captured, and a resume that skips already-succeeded entries on re-tap. Ordering must respect cross-references (dependencies before dependents) — the builder already "resolves cross-references," so topologically order the selected manifests. Effort medium (UI + sequencing), impact throughput-only but real.

**RQ2 (exempt pure-read capture manifests from the one-tap rule).** Yes, and it is the clean reading of the gate: the doctrine reserves a human tap per *write* batch; "reads are not writes" is stated in the brief. So a **separate, always-allowed panel action for read-only capture manifests** does not erode the write gate — it is the same logic as W6-RQ3's standing verification. This directly de-conflicts the board's "when Terr clears **or as free probe**" tension where probes currently compete for write taps. Guardrail: the read action must be incapable of issuing a mutation (call-allowlist to `*.get`/list endpoints only) so it cannot become a write side-door.

## W9. The lookup layer is fresh only by accident of the last harvest

**RQ1 (per-shard freshness metadata for capture-or-trust in one fetch).** Give each shard a small header carrying **source stamp (generation time), age-at-generation, and row-count delta since prior generation** — the same three signals RAG systems attach per chunk (source metadata + freshness) and that answers/INDEX already partially carries (stamp + "fresher takes a capture" rule). Put the per-shard metadata in the shard header itself (so reading the shard answers "trust or capture" in the *same* fetch), and keep INDEX as a one-screen table of shard → stamp so the phone view stays small. This lets a consumer decide without a third fetch.

**RQ2 (retention policy: generation-based squashing).** Sound, precisely because `answers/` is a pure function of `harvests/`. The safe idiom is **keep latest N bundles verbatim, roll older ones into the seed catalog, then squash their commits** (git `--squash`/interactive rebase folds the superseded inbox commits so `.git` doesn't bloat). Because answers/ can be regenerated from seed+inbox at any time, squashed history loses no *derivable* state — only redundant intermediate bundles. Flag the standard caveat: squashing rewrites history and requires a force-push, so gate it behind a manual, scheduled "compaction" run, never an auto-trigger, and keep the seed as the durable audit floor. This answers the unpoliced "what happens at 50 bundles" gap with a bounded-N policy.

**RQ3 (naming scheme for exactly two fetches, fetcher can't glob).** Deterministic shard keys published in INDEX: `answers/<pool>/<shard-key>.json` where the shard-key is computable from the lookup (e.g. first char / id-range / pool name) and printed in INDEX's table. Then a single-entity lookup is exactly **INDEX → shard** (two fetches), never a directory scan — the hard requirement for a fetcher that cannot glob. This is the Stage-4.5 per-pool + hot-shard layout the brief already flags as prior art; the naming rule is what guarantees the two-fetch bound. Effort low–medium, impact accuracy for fetch-only consumers.

## W10. Credential surface: one PAT in pasted prose, one token in a panel

**RQ1 (what actually reduces risk on a paste-only channel).** Ranked by risk reduction per effort: **(a) move all container git writes behind a `workflow_dispatch` relay** — the container pushes to a branch (or calls a dispatch) and an Action with the repo-scoped, auto-expiring `GITHUB_TOKEN` performs the privileged merge/commit. This is the strongest structural fix: per GitHub docs "the `GITHUB_TOKEN` expires when the job finishes or after its effective maximum lifetime" (max 6 hours on GitHub-hosted runners), so the long-lived plaintext-in-prose PAT can be downscoped or eliminated for writes. **(b) A second, write-only PAT for the panel distinct from the container's**, so the two exposure channels have independent blast radius and rotation. **(c) Shorter-lived PATs on a rotation ritual** — weakest, because the paste channel repeats every session and manual rotation is the thing that slips. The container receives secrets only via pasted text (no secret store on that path), so (a) is what removes the secret from the hot path; Actions "has proper secrets," which is exactly why the relay belongs there. Note the read side already avoids auth where it can (raw CDN + 60/h unauthenticated api.github.com).

**RQ2 (fail-closed multi-secret scrub gate).** Yes — `scrub.yml` should **fail-closed when the scrub list is unset** (today it *warns*, which the brief flags), and it should take a **list** of patterns (both current tokens plus any future ones), because the repo is public and a slipped string is world-readable. The standard pattern is a secret-scanning gate that treats "no patterns configured" as a build failure, not a pass — the same fail-closed philosophy as W1/W4 gates. Prior art shape: gitleaks/trufflehog-style multi-pattern allowlists run in CI; here a stdlib grep over the diff for a pattern list, exit 1 on any hit *or* on empty pattern list. Effort low, and it hardens a channel that repeats every session.

## W11. Heavyweight references price accuracy against tokens

**RQ1 (section-addressable docs: stable anchors + generated TOC-with-byte-offsets).** RAG chunking research gives measured guidance that section/heading-based ("syntactic") chunking outperforms fixed-size splitting for structured docs (IBM), and that retrieval-sized chunks in the ~200–800-token band balance context against precision (multiple chunking studies). Heading-depth matters: shallow hierarchies lose contextual granularity while very deep ones over-fragment, so a small fixed heading depth (2–3 levels) is the practical target for these reference files. Concretely: give each section a stable anchor id and generate a per-file TOC mapping anchor → byte-offset range, so a session can `web_fetch`-then-slice or `sed`-range a single section instead of reading ai.md whole (67.7 KB / ~17 K tokens). Payoff is largest exactly on the heaviest files (ai.md, quest.md, pipeline.md). Constraint honored: files stay single for skill packaging; the TOC is a generated sidecar. (The specific "3-level hierarchy is optimal" figure appears in the chunking literature but I could not pin it to a single verifiable source, so treat heading depth as a tune-it parameter, not a hard constant.)

**RQ2 (generated "task packs" vs section retrieval).** Task packs win on both tokens *and* reliability, and they are the better fit here. Rationale: the brief's own "read the one that owns the task" doctrine is already a routing table; a generated `packs/<build-type>.md` (build-type → concatenated minimal excerpt set: the owning reference's relevant sections + the laws relocated for that type + the pipeline steps that apply) collapses the ~30 K per-task read to the excerpts that matter, rebuilt by `skillpack.yml` whenever canon changes. This is the "three artefacts, one projection task instead of three inventions" pattern (understandingdata doc-drift piece) and mirrors Agentless's pre-computation approach (arXiv 2604.03515: fit the needed code into one prompt rather than accumulate). Section retrieval (RQ1) is the fallback when a task needs an off-pack paragraph. Recommendation: build task packs as the primary lever; keep anchors+TOC for ad-hoc slices. Effort medium, impact the biggest per-task token win.

**RQ3 (right budget instrument).** A per-session token ledger emitted at close (files read × sizes), written by `session_close.py` (W2) into the digest. This keeps the cost "measured instead of vibed" — the explicit ask — and gives Session 3 a baseline to regress against. It is the same instrumentation logic as the audit's own byte/token table; make it a standing output, not a one-off.

## W12. Art loop depends on an external generator and a lying preview

**RQ1 (mechanizable raw-QC checks within stdlib-image limits).** Python stdlib has no image decoder, but pure-Python single-file PNG readers establish feasibility within the stdlib-only gate (PyPNG/`png.py` is "pure Python and has no dependencies"; `simplepng.py` "reads and writes the binary structure of PNG in pure python"). Since `chroma.py` already lives within the stdlib limit (38/38 selftest), the mechanizable pre-processing checks that cost zero human looks are: **(1) flat-field chroma coverage %** — count background-key pixels vs total to reject art that fills too little/much of the frame; **(2) edge-halo / fringe detection** — scan the border ring for non-key, non-subject pixels (the "weird dark edges" premultiplication artifact named in the Cloudinary guide) to catch matte halos the square preview hides; **(3) aspect sanity** — read width/height from the PNG IHDR chunk and flag non-spec aspect ratios, directly countering the "preview lies through a square widget" failure that already caused one wrong re-export. All three read pixels/headers only — no writes, no external service, no franchise content.

**RQ2 (minimal hit-rate ledger for evidence-driven scaffold editing).** A single append-only `art_ledger.json` (or `.jsonl`) row per generation: **prompt-scaffold id → accept/reject → reason-code** (e.g. `halo`, `wrong-aspect`, `low-coverage`, `unprocessable`, `art-direction`). This is the minimal "scaffold-id → outcome" ledger that turns scaffold editing into an evidence loop, mirroring the ESLint rule-id→outcome and the batch-job "which rows didn't land" ledgers. Location: put it where `shotlist.py` can read it (same skill data dir), so shotlist can rank scaffolds by observed accept-rate and escalate to a reference image (the currently-proposed 3-failure rule) on evidence rather than vibe. Effort low, impact throughput + shipped-quality accuracy; most decoupled from the rest of the stack.
