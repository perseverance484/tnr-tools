## F.1 The recommendation in one page

**Recommended: extract a headless `ForgeCore` first, then replace the shell against it, screen by screen. `arch-core-shell` is the base, amended in two places by `arch-evolve`.**

The recommendation is not "evolve" and not "replace the UI in one bet". It is the sequenced form of both: phase 0 measures, phase 1 moves domain logic below the seam with the UI byte-identical, and only then does the shell change, one destination at a time, with the class names that today's tests select on preserved (`D_VISUAL_SYSTEM.md` D2.6 S1 already states that constraint).

**Why the core comes out first.** The seam is already in the right place below `ui/`: A.2 marks every `storage`, `transport`, `budget`, `runner` and `reconcile` module UI-independent, and the leakage runs the other way. `forge/src/ui/app.mjs` owns `harvestEntry` (`:29-47`), `resumeBlockedReason` (`:159-163`), `blockedPaths` (`:166-170`), the confirm policy (`:172-175`), the picker and its cache write (`:186-207`, especially `:198-200`), `selectManifest` (`:209-225`), the drive loop and its outcome wording (`:228-300`), `resolveCaptures`/`_materialize` (`:323-366`), `exportJob` (`:369-406`) and `_persist` (`:408-410`). That list is exactly what A.12 names as "what a second shell would otherwise duplicate". Any option that grows the UI before moving it duplicates the leak into the new surface, and R-13's own mitigation is "phase 0 moves domain logic below the UI seam first".

**What is preserved unchanged.** `storage/journal.mjs` including the `TRANSITIONS` table (`:39-47`) and `jobOutcome` (`:76-88`); `storage/compat.mjs` and the retained Builder keys `tnr_bk_idmap_v1` and `tnr_bk_gh_v1` (`compat.mjs:4-5`); every `transport/` module including the audited registry that throws before any fetch (`procedures.mjs:70-72`); `budget/bucket.mjs` and `budget/reader.mjs`; every `runner/` module except one additive hook; `reconcile/reconciler.mjs`; `ui/takeover.mjs`. That is the reviewed part of the tool and the part carrying the deep test cover: 293 cases across 13 files, with 75 adversarial, 45 auth, 30 envelope, 23 full-capture, 21 runner, 19 journal and 16 budget (`evidence/forge-tests-ci.json`).

**Why "evolve versus replace" is the wrong first question.** Both framings assume the UI is where the decision lives. The measurable facts say otherwise: the layer under `ui/` is sound and deeply tested, the layer inside `ui/` is thin and carries domain logic that does not belong to it, and the expensive mistake available here is not choosing the wrong renderer but growing a three-to-five times larger surface on top of a seam that leaks. So the first decision is where the boundary is and how it is enforced; the renderer follows from the no-innerHTML law almost mechanically (F.5), and the sequencing follows from where the test cover is (F.2).

**The one execution-core change.** `runner.mjs` gains a structured event emitter beside the existing injected `log` callback (`runner.mjs:91`). A.12 records `JobProgress` as the one component with no structured source ("no structured 'waiting for response' event"), and today `app.mjs:266` copies log strings into UI state. The emitter is advisory: it may not write the journal and may not advance an item state, and an adversarial test asserts that a throwing subscriber leaves journal bytes, write order and the transition sequence identical. This is the single edit R-13 guards, and it should be reviewed on its own SHA.

**Two amendments taken from `arch-evolve`.** First, storage: manifest and repository text moves out of the game read cache (`app.mjs:198-200`) into a **separate IndexedDB database**, not into a third store at `tnr_forge` v3. `captures.mjs:120` opens `DB_NAME` at `DB_VERSION` (`:34`, today 2), and an older bundle requesting v2 against an existing v3 database fails to open, which would take the capture cache and every full-capture snapshot with it. Rollback for every phase is re-pinning `@require` to the previous release commit (`forge_loader_user.js:12`; `.github/scripts/pin_release.py:24-29`), so a one-way door in the cache is avoidable and should be avoided. Second, measurement: `arch-evolve`'s phase E0 commits a deterministic DOM serialization of today's five screens **before** anything moves, and the acceptance gate for the extraction phase is that those fixtures come back byte-identical. That turns "move ten blocks, change nothing" from an intention into a mechanical test.

**One correction taken from `arch-replace-ui`.** `h()` assigns any non-string value to a matching element property (`forge/src/ui/dom.mjs:11`: `else if (k in el && typeof v !== "string") el[k] = v;`). For the key `innerHTML` with a non-string value that is a live HTML-string sink, and neither the build gate (`forge/build.mjs:33-37`) nor the source grep (`forge/test/ui.test.mjs:29-34`) can see it, because the literal never appears in `forge/src`. It is not reachable at `main@305a28f` (no computed attribute key and no attribute spread exists in `screens.mjs` or `app.mjs`), but a registry-driven UI that renders fields from generated contracts (RB:95-113) is exactly where a computed key appears. `h()` gains a deny-list that throws for `innerHTML`, `outerHTML`, `srcdoc` and `insertAdjacentHTML` for any value type. Tier: Source-verified for the code path; the exploit shape was probed in jsdom by the option author and is not re-run here.

Two of these axes decided it. The recommendation must answer q3 with something a reviewer can run, which only the third option does; and it must not open the reviewed execution core, which the first and third do only through one additive hook that is itself testable. The bundle axis is the reason the second option lost rather than the reason the third won.

**What the recommendation deliberately does not decide.** Whether the bundle ships minified (K-14), the destination list and navigation model the shell renders (K-02, K-20), the confirmation level the decision gate enforces (K-12), capture classification (K-06), registry expansion (K-17), the credential model (K-15, K-26), Builder retirement timing (K-11) and every other open `K` entry. The architecture is built so each of those is one place to change, not a rewrite.

### F.1.1 What an auditor can check without taking the recommendation on trust

Every load-bearing claim above is mechanical and socket-free. The eleven cross-seam imports are a grep of the import lines in `forge/src/ui/app.mjs` and `forge/src/ui/screens.mjs`. The eleven-to-zero ratchet is a static test of the same shape as the existing source-wide sink grep (`forge/test/ui.test.mjs:29-34`). "The execution core was not opened" is a per-phase file list under five directories, expected empty for a shell phase. "Behaviour did not move during the extraction" is a byte comparison of DOM fixtures committed before the move. "A second host can drive the product" is one committed test that runs the whole lifecycle with no DOM global. "No event leaks a credential or a body" is a static forbidden-string test modelled on the one already in `forge/test/auth.test.mjs`. "No control can send while an item is ambiguous" is a walk of every rendered control's handler against a core allow-list, not a reading of the markup. None of these requires a browser, a socket or a live request, and none of them is an opinion.

## F.3 Brief §12 questions, answered

Each answer names its evidence and the decision it depends on. "None" means the answer does not wait on a director ruling.

**q1. Evolve the current Forge UI in place, or replace the UI layer while preserving runner, storage and transport?** Replace the UI layer, but in two stages, and preserve runner, storage, transport, budget and reconcile byte-for-byte except the one additive emit hook. Stage one extracts the core with the UI unchanged; stage two replaces the shell against the core, screen by screen with class names preserved. Evidence: A.2 already marks everything below `ui/` UI-independent; `app.mjs:6-13` and `screens.mjs:4-6` are the eleven cross-seam imports that measure the leak; R-13's mitigation is the extraction-first ordering. Depends on: none for the ordering; K-02/K-20 decide what the replaced shell renders.

**q2. Do the vanilla DOM and CSSOM constraints remain required, or can a component strategy improve maintainability?** The constraints remain, and the maintainability win comes from the view-model seam rather than from a renderer. Every tagged-template library materialises markup through an HTML string sink, which `forge/test/ui.test.mjs:29-34` greps for across all of `forge/src` and `forge/build.mjs:33-37` re-greps in the built bundle and throws on. Preact would pass that law but adds a runtime dependency to the device that performs live writes, plus a compile step, to solve a re-render problem a region helper solves in about 90 lines; `superjson` is the only runtime dependency today. The component strategy adopted is: pure view-model builders in `core`, pure `render(viewModel)` factories in `ui`, and a region helper in `dom.mjs`. Honest cost: the 25-component inventory in A.12 is enforced by committed fixtures rather than by types. Depends on: none; this is an engineering judgement, and adding a runtime dependency would be a director-grade supply-chain decision if it were ever revisited.

**q3. How is the execution core kept UI-independent enough for future shell or native hosting?** Make it a machine-checked invariant, not a convention. Three mechanisms: `ForgeCore` is constructed inside `compose()` and is the only object a host receives; a static test asserts no file under `ui/` or `hosts/` imports from `runner/`, `storage/`, `transport/`, `budget/`, `reconcile/` or `github.mjs`, ratcheting today's eleven violations to zero; and a committed headless host test drives plan, decision, run, pause, reconcile and export through the public API with no DOM globals at all. If that test needs a DOM, the boundary has leaked. Two hosts already exist to justify it: the node harness that calls `compose()` (`forge/test/compose.mjs`), and the Quest Studio shell, which mounts outside `compose()` (`824c4d58:forge/src/main.mjs:151`) and consequently re-invented its own state, its own colours (`824c4d58:forge/src/studio/ui.mjs:12-60`) and its own confirm. Depends on: none.

**q4. Manifest schema compatibility and versioning.** No manifest contract change in this programme, and backward compatibility is the first principle rather than a courtesy: every validated manifest under `push/` and `archive/spent-manifests` must keep parsing and running unchanged. `runner/manifest.mjs`, `validate.mjs`, `lints.mjs`, `pool.mjs`, `refs.mjs` and `recipes.mjs` are preserved (F.2), and the pre-send refusal of unknown keys stays as it is, because it is the fail-closed half of the contract. Three forward-compatible moves cost nothing now and are worth taking. Second, a work package is addressed as `{source, ref, path}` rather than as a file name on one branch, which is what lets a Studio build and a workstream package arrive without a second parser (q11, F.7). Third, the manifest hash already computed during selection is recorded on the job, so a promotion or a re-run can prove which bytes were planned. Depends on: none now; the parity slices depend on K-11 for their urgency and K-17 for their read surface.

**q5. Storage migration and compatibility for existing journals, capture cache and settings.** Four stores, three rules. Depends on: the two-release rule is recommended here and is routed to K as a new entry (F.18).

**q6. Capture data classification and persistence/export rules.** F.11. Three tiers, the allowlist stays fail-closed, and the tier is a property of the procedure and the destination rather than of the operator's intent. Depends on: K-06, with K-17 bounding what can be read at all.

**q7. Procedure registry expansion and source-drift gates.** Expand nothing as a side effect of architecture. **q8. Content-type adapters and forms for admin editing.** Adapters are data, not code branches. A content class contributes three things: a field projection derived from the generated contracts, a capability row from E saying what the game actually permits for that class, and a lifecycle axis saying which field, if any, carries publication. The shell renders whatever the projection declares and nothing else. Three consequences follow and each is a rule. No admin form may exist for a class whose write path E marks unavailable, because a form that cannot submit is an invented capability (R-16). No adapter may encode a rule the generated source does not carry, which is the same registry-driven rule as F.9 applied to a different surface. And a class with no lifecycle field gets no publish control at all rather than a disabled one that implies the field exists: `PublishControl` and `AdminReviewCard` have no source today (A.12 marks both "none (HOLD)") and WCM §23 forbids implying the capability (WCM:611-629). The architectural work is therefore the projection pipeline, not a form library. Depends on: K-05 (which classes get first-class forms in v1), K-03 and K-04 (permission scope), K-53 (whether balance-bearing classes appear at all), K-52 (how the surface learns the signed-in account's role).

**q9. Preview strategy per content class.** Architecturally, preview is a read plus a renderer, never a claim, and it sits in three tiers. Tier one, and the only one available for every class Forge touches: a structured record view built from a fresh live read, stamped with the read time the reader already returns (`budget/reader.mjs:40` carries `cached` and `at`), showing the fields as the game holds them. Tier two: a faithful client-side render where the game's own renderer can be reached at the same origin without reimplementation, which is a per-class finding in E rather than a general capability. Tier three, and preferred over any imitation: a deep link into the game's own surface for the record, which costs nothing and cannot lie. The binding rule across all three is WCM §23's: a preview claims no fidelity without a source path, so a tier-one view must say it is a record view and not a player-facing render. Reimplementing a renderer in Forge is rejected outright, because it creates a second rendering of canon that can disagree with the game, which is what `RUL-2026-09-12-002` forbids. Depends on: K-05, and E's per-class findings for what a preview can be built from at all.

**q10. GitHub repository bridge and PAT handling.** F.15. One transport (`github.mjs`), one typed operation list above it, one credential key shared with Builder (`compat.mjs:5`), reads that need no credential at all on a public repository (`github.mjs:22-27` adds an authorization header only when a PAT is stored; `:50-57` refuses a write without one). Depends on: K-15, K-26.

**q11. Workstream integration and discovery.** F.13. Depends on: K-28, K-40.

**q12. Result and harvest contract evolution.** The bundle stays the same document, produced by the core instead of by `ui/app.mjs`. Depends on: K-06 for bodies; the `checks` fix is a repository-consumer contract change and is routed as its own Lane A item (F.17).

**q13. Audit and history model.** Do not add a store, and do not merge the histories into one voice. Depends on: K-09 for where approval events live; K-47 for annotations.

**q14. Bundle size, performance and startup on mobile.** Three levers, ranked by measured effect. Minification is the largest and is not an architecture decision: 397,984 bytes to 232,720, gzip 74,969 to 52,556 (A.9), and it is K-14. Deferred contract construction is second: the three inlined JSON blobs are the largest single cost in the bundle (A.9 attributes `nested.json` 96,267 and `fields.json` 10,349 raw within `src/runner`'s 204,172, plus `32b_DATA_pool.json` 21,934) and they are evaluated when the IIFE runs on every game page the loader matches, including pages where boot returns immediately. Emitting them as function bodies constructed on first use moves that work behind the arm marker; the option authors measured roughly 0.25 ms and about 125 KB of retained heap per unarmed page in node, which is real for eviction pressure and is not a boot transformation. Firefox Android behaviour is Inferred. Third, the split itself costs bytes rather than saving them: roughly +31 KB unminified for the core layer plus the roughly +18 KB the visual system already budgets (D2.7). A CI ceiling on raw and gzip bytes per release makes growth a decision rather than a discovery. Depends on: K-14.

**q15. Release, pin and install strategy.** One bundle, one `@require`, unchanged. Two hosts do not mean two artefacts: the userscript host and the headless host are entry points in one tree and only the userscript entry is bundled. A second pinned file would change the release contract, because `.github/scripts/pin_release.py:24-29` raises unless exactly one `@require` per bundle is found and `forge/tools/check_release_pin.mjs:28-34` requires it to resolve to an immutable commit URL. Rollback for every phase is therefore the same one-line operation, which is why the journal must stay downgrade-readable (q5). Phase 0 lands the marker-only relaxation and its integration plan records that the ChatGPT branch carries one too (R-11, R-22, K-60). Depends on: K-14 for the artefact shape. Landing the fix is engineering, not a director assignment: the one-writer rule reserves a branch to one writer, not a file to one branch (`docs/DEVELOPMENT_WORKFLOW.md:112`), and an earlier draft of this sentence read it the other way.

**q16. Recovery after tab eviction, crash and network loss.** The mechanics are unchanged and deliberately so: `SENT` is flushed before the request, a job holding `SENT` refuses to run, resume reconciles first, a transport failure becomes a `NETWORK` pause recorded through `_pause` (`runner.mjs:226,632-636`) and never a retry, and a 429 persists the trip marker. What the architecture adds is that recovery becomes a core query rather than UI state, so a fresh host, a reloaded tab or a test reconstructs the whole picture from one call, which is what makes "recovery is a screen, not a toast" implementable without new state. It also removes a real defect: the results card is prepended to the main region (`app.mjs:177`) and the drive loop's refresh replaces that region (`app.mjs:264-300`), so with GitHub sync off the operator's only copy of a bundle is wiped by the next render. Depends on: none.

**q17. Accessibility, touch and keyboard behaviour.** The 44 px floor becomes uniform by removing the two sub-floor exceptions (`styles.mjs:25,27` against `:31`), and a static stylesheet test asserts no interactive selector sets a smaller minimum. Region re-render is itself the accessibility fix: today the 1500 ms whole-region replace during a run (`app.mjs:268`) would discard focus, scroll and any half-typed value, including the orphan-adoption input, which is the highest-consequence input in the tool. Every action stays a real button or input; the decision surface is a focus trap whose initial focus is the safe choice and whose Escape dismisses without approving; no keyboard shortcut ever triggers a mutation or a publish. State is carried by word plus construction as well as colour, so nothing state-bearing depends on glyph coverage or on the OS forwarding a preference to a userscript overlay, both Inferred. Depends on: MOB and ACC own the targets; K-02/K-20 own the destinations.

**q18. Test architecture for a much larger UI and capability surface.** Five layers, four of them socket-free node tests as today, plus one browser smoke only the user may run. Unit: core facades and view-model builders as pure functions with no jsdom, which is where the assertions currently tangled in `ui.test.mjs` belong. Contract fixture: keep every existing suite unchanged, add `github.mjs` and `upload.mjs` contract tests (zero today), add a real-journal fixture corpus for any future migration, and add a `validate.py --parity` case. UI contract: committed view-model goldens per screen and state, enumerated over the journal's own transitions table (`journal.mjs:39-47`) so no legal state is unrendered, plus a thinner jsdom layer for roles, names, target sizes and the absence of an HTML sink, plus the 13 semantic guarantees AUD §17 lists mapped one-to-one onto named tests (R-27). Adversarial: no rendered control reaches a send path while an item is `SENT`; no event payload or snapshot contains a record body, a PAT or the strings `auth.test.mjs` already forbids; a throwing subscriber changes nothing; the import-direction gate. Browser smoke: user-only, read-only first, and no agent may run it. Playwright or any real-browser CI layer stays out unless the director rules otherwise, because tests are socket-free by repository rule. Depends on: a new K entry on whether a real-browser test layer may ever exist (F.18).

## F.5 UI technology and its constraints

**Technology.** `document.createElement` through `h()` (`forge/src/ui/dom.mjs:3-16`), one CSSOM sheet installed through `installCss` with its `adoptedStyleSheets` path and `insertRule` fallback (`:30-42`), pure `render(viewModel)` factories, a region helper for event-scoped subtree updates, and `createElementNS` for the D2.4 atmosphere and glyph work. Zero new runtime dependencies.

**No innerHTML.** The rule holds by construction and by three gates. Construction: no string-to-DOM path exists anywhere in the recommendation; there is no template, no parser and no markup join. Static gate: `forge/test/ui.test.mjs:29-34` walks all of `forge/src` and fails on `innerHTML`, `outerHTML`, `insertAdjacentHTML` or `document.write`. Build gate: `forge/build.mjs:33-37` re-greps the bundled output and throws, so a future dependency cannot smuggle a sink past the source walk. Runtime gate, new: the `h()` deny-list from F.1, which closes the hole at `dom.mjs:11` that both greps are structurally blind to.

| Rejected | Why, specifically |
|---|---|
| lit, uhtml, htm with templates | Their mechanism is an HTML string: a tagged template is joined into markup and assigned to a template element, then cloned. That trips both gates, and worse, it makes "no HTML string sink" unenforceable by the only enforcement Forge has |
| Preact plus hooks | It would pass the law on construction, but the build gate greps the shipped bundle text, so a minified property assignment inside the dependency trips it; narrowing the gate to source only would remove exactly the case it exists to catch. It also adds a compile step between source and bundle, which is what makes "a fresh build equals the checked-in bundle" a cheap CI assertion today |
| Solid, and micro-libraries such as van | Same template-cloning problem for the first; for the second, a dependency for something measured at about 3 KB in-house, with no DOM-only guarantee and no audit trail in this repository |
| Web Components with shadow roots | Style isolation is already solved by scoping every token to the overlay classes with a contract test, and shadow roots would break the existing jsdom text assertions and the Builder-suppression observer contract |

**Single bundle at `@require`.** One esbuild IIFE, one `@require` pinned to an immutable commit (`forge_loader_user.js:12`), no dynamic import, no second artefact, no CDN asset, no web font, no data-URI pack. "Lazy" in this plan always means deferred construction, never deferred fetch: the recovery story assumes the bundle is already in the browser, and a second URL is not covered by the pin.

**Size budget.** A CI assertion on raw and gzip bytes per release, failing a phase that exceeds its declared delta, alongside the existing bundle-reproducibility job that proves the checked-in bundle equals a fresh build. The baseline is A.9's measured 397,984 raw and 74,969 gzip. The honest expectation is that the artefact grows: roughly +31 KB unminified for the core layer, roughly +18 KB for the visual system (D2.7), plus whatever the component inventory costs. The only large downward lever is K-14.

**The cost of refusing a component library, stated plainly.** Twenty-five components rendered by hand are enforced by convention plus committed fixtures, not by a type system. A twenty-sixth construction can be added that no test names. That is the real maintainability price, it is why F.3 q18 leans hard on view-model goldens and per-component fixtures, and it should be put to the director as a known trade rather than argued away.

## F.6 Repository operation contract

RB §6 is the binding vocabulary (RB:150-183). Forge sends named requests rather than bespoke GitHub calls scattered through screens: load project/source; load subtype registry/policy; save draft revision; compile quest source; validate package; search/reuse evidence; generate artifact requirements; fetch build result; open generated manifest (RB:156-164). The repository side returns a machine-readable envelope carrying status; source revision/SHA; compiler/tool revision/SHA; **requested operation**; result data; blockers; warnings/advisories; generated artifact pointers/hashes; provenance/evidence pointers; and **next legal actions** (RB:166-177). RB §7 bounds what may be executed: a build request chooses from approved operations and adapters, and the browser never receives permission to execute arbitrary repository code (RB:185-200).

| RB §6 operation | Status at `824c4d58` | Note |
|---|---|---|
| load project/source | partial | the source is read from the request branch; there is no project identity in Quest Source v1 (A.11 gap (i)) |
| load subtype registry/policy | yes | the registry and the profiles are fetched when the Studio opens |
| save draft revision | yes | branch-scoped write of the request document |
| compile quest source | yes | source-push trigger (RUL-2026-09-16-002; not workflow dispatch at the accepted SHA), trusted-checkout separation, pushed-ref worker-definition equality |
| validate package | no | not a separate operation; validation rides inside compile |
| search/reuse evidence | no | none |
| generate artifact requirements | partial | the shot list is produced inside compile, not requestable on its own |
| fetch build result | yes | polled from the request branch, with stale detection against the submitted commit |
| open generated manifest | partial | a path guard exists, but only a text view; promotion into the runner is F.7 and K-39 |

**v1 at 824c4d58 implements a subset; the extensions are roadmap items, not slice defects.** The build-result envelope at that SHA carries `schemaVersion`, `kind`, `requestId`, `subtype`, `status`, `resolvedEngineType`, `blockers`, `errors`, `warnings`, `generated`, `art`, `validation` and `provenance`, with `liveGameTouched:false` (`824c4d58:skills/building-tnr-content/scripts/quest_compile.py:212-233`; `824c4d58:forge/src/studio/repository.mjs:41-49`). Measured against RB §6 it lacks the requested operation, a generated-manifest hash, package readiness, next legal actions and a structured decisions section (A.11 gap (b)). Each of those is an extension to plan, not a defect to fix on someone else's branch.

Two properties make this a contract rather than an implementation detail. First, the transport may change: the exact transport is initially GitHub Contents plus Actions and may later become a thinner purpose-built service, and RB is explicit that the product contract depends on request and result semantics, not on the provider (RB:181). Second, the operation list is closed: a static test asserts no ad-hoc repository path is reachable from `ui/`, so the browser cannot widen the boundary by accident. The sync-state vocabulary that rides on every operation is RB §11's (F.8).

**Why the operation list must be closed, in one paragraph.** An open list is a remote-shell architecture with extra steps, which RB §7 rejects by name (RB:185-200). A closed list has three properties worth the constraint: a reviewer can enumerate everything the browser can cause the repository to do; a token's required scope is derivable from the list rather than from a search of the code; and the worker executes trusted, reviewed code from a pinned tool revision against the authored source revision, so reproducibility is a property of the operation rather than of the operator's care. The test that keeps it closed is static and cheap: no ad-hoc repository path is reachable from `ui/`.

## F.7 Studio to runner promotion contract

**The rule.** Promotion is a journaled import of an envelope-named manifest into the same preflight as a `push/` manifest. There is no Start control in the Studio.

QS §8.7 requires that when a build is valid the Studio can load the generated manifest directly into the existing Forge planning and runner path, that the user then receives the normal live-consequence preflight and explicitly starts the live operation, and that the build service must never turn Compile into a live-game write (QS:306-312). QS §15.8 restates it as an acceptance point: a valid output can be opened directly in existing preflight, and nothing contacts the live game until the operator explicitly starts the existing Forge run (QS:459). `RUL-2026-09-12-001` is the ruling that removes the mechanical relay (`docs/RULINGS.md:141-152`).

**What promotion is.** The bytes named by the envelope under the request's build directory are fetched, parsed by `parseManifest` and planned by `planOrder` exactly as a `push/` manifest is, validated by the same validator and gated by the same auth check at the moment of the tap, and the resulting job is journaled with provenance recording the Studio branch, the source revision, the compiler revision and the generated-manifest hash. The only bytes the runner accepts are the ones the envelope names; the safe-path guard that accepts only paths under the request's build directory already exists at the seam and is preserved.

| Step | What happens | What is journaled | What is refused |
|---|---|---|---|
| 1. Result is valid | the envelope names a generated manifest path and, once F.6 is extended, its hash | nothing yet | a result whose source revision differs from the submitted commit is stale, never current |
| 2. Fetch | only the bytes at the envelope-named path under the request's build directory | nothing yet | any other path, by the existing safe-path guard |
| 3. Parse and plan | the same `parseManifest` and `planOrder` a `push/` manifest goes through | the plan, with the manifest hash | a manifest the validator rejects; there is no second validator |
| 4. Preflight | the same derived mode, counts, problems, warnings, blocked paths and images | the selection | nothing new; this is the existing surface |
| 5. Decision | the operator resolves a decision hashed over this exact plan | the decision reference | a decision resolved for a different plan |
| 6. Start | the existing runner, under the existing auth gate re-read at the tap | the job, with provenance: Studio branch, source revision, compiler revision, generated-manifest hash | a start from inside the Studio; there is no Start control there |

**What promotion is not.** It is not a new execution path, not a second validator, not a bypass of the preflight, and not a Start button inside the Studio shell. The failure mode R-18 names is precisely a rushed promotion that skips `parseManifest`, `planOrder` or the auth gate.

**Why a hash is required and not yet available.** The envelope at `824c4d58` records no generated-manifest hash even though QS:285 lists one (A.11 gap (h)), so Forge cannot yet prove which bytes it would hand to the runner. That extension is part of F.6 and is a prerequisite for promotion, not an optional nicety.

**Status.** The contract itself is **K-39** and is not authored here. What this section fixes is the shape any authored contract must have, so that a later brief cannot quietly produce a second path into the runner.

## F.8 Studio state model and journal v2

**The problem.** At `824c4d58` the draft and the last result live in one `localStorage` key with one draft per device (`824c4d58:forge/src/studio/ui.mjs:10,146-158`), build state lives in memory, `requestId` is derived from the device clock (`:62-64`), and polling stops when the shell is hidden. Two devices cannot share a draft and a tab eviction mid-compile loses the in-memory state (R-18).

**The model.** Studio drafts and build results become durable per-request records: `{requestId, sourceCommit, syncState, lastResult}`, one per request rather than one per device, wired through `compose()` so the composition every harness calls covers them (A.11 consequence 6). `syncState` takes its values from RB §11 (RB:271-280): `Draft saved locally`, `Repository revision saved`, `Build requested`, `Building`, `Build result received`, `Repository unavailable / retry save`, `Build failed`, `Build blocked by design decision`. RB is explicit that a user must not lose authored work because GitHub, API or worker access fails, and that local durable draft persistence plus explicit repository-sync state is part of the architecture (RB:282-286). At `824c4d58` a failed save and a failed dispatch both surface as one "Repository request failed" although the source may already be committed, so `Repository revision saved`, `Build requested` and `Repository unavailable / retry save` are not yet distinguishable.

**Cases the model must state.** Multi-draft on one device: each request is its own record, so a second draft never replaces a first. Cross-device: a draft is durable locally and its repository revision is durable in the request branch, so another device resumes from the branch rather than from the first device. Tab eviction mid-compile: the record survives with `Build requested` or `Building`, and the poll resumes with backoff (F.14) rather than the state being lost. Studio build states live on the content-lifecycle axis, never on the execution lifecycle: a mechanically valid build must never render as a successful execution or as a publication.

| RB §11 state | What produces it | What it must never be rendered as |
|---|---|---|
| Draft saved locally | a local durable write succeeded | a repository revision |
| Repository revision saved | the branch-scoped write returned success | a build having been requested |
| Build requested | the dispatch was accepted | a build having started |
| Building | a run is known to be in progress | a result |
| Build result received | a result document was read at the submitted revision | a successful execution or a publication |
| Repository unavailable / retry save | a save or a dispatch failed, with the failing half named | a lost draft |
| Build failed | the compiler ran and failed | a director decision being missing |
| Build blocked by design decision | the compiler refused for a missing decision | a tool defect |

The last two are the pair F.17's first row protects: they are distinguished today by matching prose, so the vocabulary is only as reliable as the compiler's wording until a structured code exists.

**Journal v2.** The job-level repository sync state is a journal fact: `job.sync` taking `not_configured`, `pending`, `committed` or `failed`, journaled **before** the contents-API write so a bundle that never landed is a machine state rather than a textarea. Today `Github.put` throws on a non-2xx and `exportJob` falls back to showing the bundle as text (`app.mjs:402-405`) and the journal records nothing (A.4.1 item 4, R-07). The change is an additive migration: `MIGRATIONS[1]` in the empty table at `journal.mjs:407`, purely additive, no field renamed or removed. Three constraints bind it. It ships in a release of its own with fixtures replayed from real exported journals (`journal.mjs:400` is the export path those fixtures come from), which is R-09's own mitigation. It obeys the two-release rule from F.3 q5, because `migrate()` refuses a record newer than the running bundle (`journal.mjs:413`) and rollback is re-pinning the loader. And rollback stays readable: a v1 record is never rewritten in place by a bundle that cannot read v2, and a failed migration parks the record rather than deleting it, surfacing it through `journal.broken` (`journal.mjs:225`), which needs a renderer it does not have today.

## F.9 Registry-driven UI and generated projections

**The rule: no rule table lives in UI source. A browser lint is either derived from a registry or profile projection stamped with its source SHA, or it does not exist.**

RB §4 states the bad pattern plainly: the repository says one thing, the UI hard-codes the same thing, and one side eventually drifts; the preferred pattern is that the repository owns the fact, a generated or read adapter exposes it, and Forge renders it with provenance (RB:95-113). RB adds that Forge may bundle generated snapshots for fast startup, but every snapshot must identify the repository source SHA it represents and be rebuildable from canonical source (RB:114). QS §5 requires one registry read by both the UI and the compiler, and forbids maintaining one subtype matrix in the browser and another independently in Python (QS:150-157).

**How a projection is built and what it must carry.** A projection is generated from canonical source by a repository tool, committed, and stamped with the source SHA it was generated from, exactly as the field and nested contracts already are (A.6). Forge imports it as data and renders it; it never edits it and never supplements it with a locally authored rule. Three properties make the stamp load-bearing rather than decorative: a surface can say which revision an advisory came from, a drift job can re-derive the projection and fail on any difference, and a reviewer can tell a generated fact from a hand-written one by looking at where it lives. RB allows the bundled snapshot for startup speed precisely on the condition that it identifies its source SHA and is rebuildable from canonical source (RB:114).

**Where today's code departs.** The Studio enables a button for `id === "mission"` rather than for any supported adapter and reads no capability flags at all (`824c4d58:forge/src/studio/ui.mjs:242-246`), while the registry's six capability booleans (`824c4d58:skills/building-tnr-content/data/49_DATA_quest_studio_subtypes.json:19-26`) are read by nothing. The draft check re-encodes the profile's objective count as a browser rule (`824c4d58:forge/src/studio/ui.mjs:122-138`), which exceeds what the canonical compiler enforces: `skills/building-tnr-content/scripts/mission.py` caps enemies per battle node (`:156-174`) and mentions the objective count only in a selftest fixture (`:351`). The maturity vocabulary is also hard-coded in both languages, and the registry's three values do not match the four QS §5 proposes.

**The architecture consequence.** Advisory client checks are generated projections of registry and profile data, stamped with the SHA they were generated from, and a contract test fails when a browser-side advisory rule encodes a constraint the generated source does not carry (R-20). The maturity vocabulary is aligned in one place read by both languages. Whether the canonical compiler should enforce the profile shape at all is **K-36**, a director decision, because it changes what the canonical compiler accepts; it is routed in F.17 and not settled here.

## F.11 Capture data classification, persistence and projection

**Inputs.** `capture-model.json` does not exist at this SHA, so this section is derived by the planning owner from: B rows P-09 to P-14 and P-58; E's capture and privacy findings, including that hidden rows are readable by any account for six of the seven Forge classes (E's CC-08) and that `hidden` is a listing and play gate rather than confidentiality (R-31); `evidence/registry-gap.json` (145 unregistered procedures, of which 21 are public queries and 124 are protected); `forge/src/storage/captures.mjs`; and `forge/src/budget/reader.mjs`.

**Where the boundary sits today.** Full persistence is fail-closed and narrow: only seven audited content-record point reads may have a body written into an exported bundle (`captures.mjs:58-66`), one serialized body may not exceed 512 KiB and exceeding it is an explicit persistence failure rather than a truncated body presented as full (`:84`), and a two-way test asserts that every full-persistence path is an audited content-record point read and nothing else is. `CachedReader.list` refuses any path that is not a name list, with the message that a paged procedure needs a paged input (`reader.mjs:76`), so list bodies cannot be captured at all. Builder's behaviour is the opposite: every capture stores the full decoded body with no opt-in and no ceiling (P-12), and one committed bundle carries 1.5 MB of battle-entry bodies.

| Row | Builder | Forge 0.4.0 | Status |
|---|---|---|---|
| P-09 capture-only runs with zero mutations | read-only gate with its own procedure pattern | zero-item manifests with captures; outcome success only if every capture is ok and persisted | parity, keep in Forge |
| P-10 reads outside the audited registry | any tRPC query path can be named | the registry throws before any fetch (`procedures.mjs:70-72`) | gap, gate G-02, K-17 |
| P-11 paged or filtered list captures with an input | the input is passed through as written | the reader refuses any non-name-list path (`reader.mjs:76`) and sends no input for name lists | gap, gate G-03 |
| P-12 capture bodies in the bundle for every read | every body stored inline, no opt-in, no ceiling | only the seven allowlisted point reads, under the ceiling | gap, gate G-03 |
| P-13 field projection and scope honesty | projects array rows and stamps a scope sentence | the projection key is dropped silently and no scope is written | gap, conditional on P-10 and P-11 |
| P-14 full-capture persistence contract | not applicable: no contract, no ceiling, no separation | explicit opt-in, immutable snapshot, ceiling, fail-closed export | Forge is better; keep |
| P-58 absent record versus captured record | records it visibly as not a success, though with misleading text | a null body counts as a persisted body and toward run success | evidence-safety defect, gate G-07 |

**The gap that matters for retirement.** P-10, P-11 and P-12 are the census-to-generator loop (W-06, W-07): a paged or filtered list read whose bodies a `*.gen.py` script consumes to emit the next manifest. Twenty-three generators in the archived record read `captures[].data`. Forge cannot run that loop at all today, and that is a retirement blocker (gates G-02 and G-03), not a preference.

**Recommended tiers.** Three, as a property of the procedure and the destination, never of the operator's intent.

| Tier | What it covers | Where it may persist | Enforcement |
|---|---|---|---|
| Repo-safe | The audited content-record point reads that exist today, within the existing ceiling | The exported bundle, which is committed to a public repository when sync is on | The existing allowlist and ceiling, unchanged, plus the existing two-way registry test |
| Local-only | Bodies Forge may hold as evidence on the device but must never write into an exported bundle: anything protected, user-shaped, account-shaped or session-shaped | IndexedDB snapshots only; refused at export with a named reason, never silently dropped | A fail-closed export check plus an adversarial test that no local-only body can reach a bundle |
| Projected | A field projection of a list body, recorded with the projection that produced it and with an honesty sentence stating that absence from a filtered result is not evidence of absence | The bundle, subject to a per-entry ceiling | The projection is applied before persistence, and the entry records the input actually sent, not the input as written |

**The export rule that makes the tiers real.** Classification is worthless unless the export path enforces it, so the rule is: a body is written into a bundle only if its procedure is on the repo-safe allowlist or its entry carries a recorded projection, and any other body is refused at export with a named reason that appears on a durable surface rather than being dropped. That is the same fail-closed shape the current ceiling already has, where exceeding the limit is an explicit persistence failure and never a shortened body presented as full (`captures.mjs:84`). The corollary is that the export refusal must be visible in the run's outcome: a bundle that is missing a body the manifest asked for cannot report success, which is the existing relationship between persistence verdicts and `jobOutcome` (`journal.mjs:76-88`) and must survive any widening.

**What this does not change.** Snapshots stay immutable and are never invalidated by a write, deletion of a snapshot stays a separate and separately worded action from cache invalidation (SCR:336-359), and nothing in this section authorises broadening persistence now. It proposes the model the brief asks for instead of removing the allowlist, which is the instruction.

**Two honesty defects that must be fixed before any widening.** P-58: a point read returning null is recorded as a success with a persisted body and counts toward the run's success outcome, so an absent record is indistinguishable from a captured one; gate G-07 owns the fix. P-11: for a name-list capture the journal records the manifest's input even though the reader sends none, so the journaled input is not the sent input; gate G-03 asks for a test asserting they are equal. Neither is a classification question, and both make a widened capture surface less trustworthy, so both precede it.

**Drift gate.** Any procedure admitted to the registry for capture work carries its pinned `file:line` under the existing transcribed-from-source invariant, and the two-way relation between the persistence allowlist and the registry is asserted in both directions so a new path cannot be persistable without being audited.

**Where the UI shows the tier.** SCR §11 requires that the cache-versus-snapshot distinction is preserved, that invalidation and deletion are explained with their distinct consequences, that deletion is more deliberate than invalidation, and that a privacy tier is shown **once the architecture is finalised** with an explicit instruction not to implement the taxonomy from the UX document (SCR:336-359). ACC §11 carries the acceptance line (ACC:121). This section therefore proposes the taxonomy and leaves both the tier names and what may persist to **K-06**; the registry half is **K-17**.

## F.12 Review queue, approval state and audit

Derived from `scratchpad/design/queue-model.json`, which exists; no `synth-data.json` does.

**Recommendation: the repository review package is the queue index and the live game is the state column.** This inverts E.8's provisional hybrid and changes the storage shape from a mutable status document to append-only events.

Four reasons, each checkable. Cost: the queue is the most-visited admin screen, and every list read a live index would need is a rate-limited public procedure sharing a local reserve with the carrier game page, where a trip costs the player rather than signalling a retry; a repository index spends GitHub quota on discovery and game budget only on an opened package. Coverage: a live index cannot represent CA-06 at all, because AI records carry no lifecycle column, and cannot filter CA-04, because the asset list read takes no hidden input; those are two of the seven classes Forge touches. Semantics: every create ships hidden, so the live unpublished set is a backlog rather than a queue, and "ready for review" is a human act whose only durable record is a repository write. Write safety: `Github.put` reads the current sha and then writes with no retry (`forge/src/github.mjs:50-57`), so a mutable status document makes every second decision a conflict to recover from, while an append-only event file is always a fresh path with no prior sha and two reviewers never overwrite each other.

| Option | Where "ready for review" lives | Can approval be recorded | Decisive problem |
|---|---|---|---|
| QM-A live drafts listing | nowhere durable; it is the set of unpublished live records | no: no class has an approval, rejection or changes-requested field | the reader refuses paged lists today, two of seven classes cannot be filtered or represented, and every create ships hidden so the set is a backlog |
| QM-B workstream roadmap as the queue | a task status inside a validated enum | only by overloading an enum owned by the content workflow | per workstream, not per record; projections drift because no workflow invokes the validator |
| QM-C device-local queue | one device's storage | a local field nobody else can see | it preserves exactly the verbal relay the brief exists to remove |
| QM-D live listing indexed, repository file annotates | split: live index, repository annotation | yes, in the repository file | it puts the expensive, rate-limited, class-incomplete source on the busiest screen, and a single mutable document makes every second decision a conflict |
| QM-E repository package indexed, live read as the state column (recommended) | an immutable submission plus append-only decision events under a review directory | yes, as immutable events folded into a status | blind to anything authored in the game's own staff editor until a reconciliation sweep runs, and the sweep needs the same paged-list capability P-11 does |

**Approval storage.** A package directory under `state/`, holding a submission document plus immutable per-decision event files; status is a fold of the events, never a stored field. Four properties recommend it: the write path is already proven, the directory is disjoint from every path repository automation rewrites, it survives the approved inbox-compaction ritual, and it is readable with no credential at all on a public repository, because the client adds an authorization header only when a PAT is stored (`github.mjs:22-27`) while the write refuses without one (`:50-57`). That last property is a materially better credential story for a delegated reviewer than any option that requires a token merely to look. The rejected alternatives are recorded with their reasons: annotating the results bundle makes immutable evidence mutable and is destroyed by the compaction ritual; the workstream roadmap is per workstream rather than per record and its status enum is a contract owned by the content workflow; a commit trailer is unreadable through the three methods `github.mjs` exposes; local-only preserves exactly the relay the brief wants removed.

**Why it is not canon.** It never stores a lifecycle value, which is read live and rendered with its own read timestamp (`budget/reader.mjs:40`), and WCM §23 requires that a stale cache never masquerades as live (WCM:611-629). It never stores a content field. It stores no status, only events, so no field can disagree with the history. And the copy says it is coordination state, in the same sense the workstream packet is documented as not an authority.

**Audit model.** Four histories, each answering a different question, and the History panel is a union with every row labelled by source, because the sources have different authority. The game's own content-change log is what the server did, and it is unreadable for two of the classes Forge touches and silent on create and clone everywhere. The Forge journal is what one device believes and must never be presented as the audit; it reaches the admin only through the committed bundle. The committed bundle is what the repository can prove. The git history of the review directory is what a human decided. Questions none of them answers, and which the surface must not imply: who created a record anywhere, any history at all for AI profile rules, whether a change can be undone (there is no production or per-record restore, so the honest answer is a pre-write capture plus a compensating edit), and who read a draft.

**Composition rule.** Capture the pre-state automatically before every admin update rather than relying on a manifest to ask for it, because that is the only way the bundle can carry the before half for the two classes whose game log is unreadable. What may be persisted from those captures is bounded by F.11 and K-06.

**Prerequisites the queue cannot be built without, and which are not queue work.** Four, each owned elsewhere. No Forge write has ever run live (gate G-08), so a review package must be mintable from a Builder bundle as well, which it is, because both tools emit the same per-record entry contract the harvest tooling consumes. The results-bundle parity defect (R-19, F.17) must be fixed before a package cites a Forge bundle as its evidence. The reconciliation sweep needs the paged-list capability the reader refuses today (`budget/reader.mjs:76`), which is gate G-03. And any role read used to decide what the admin may see must be pre-checked rather than discovered by a refusal, because the transport maps an unauthorized code onto the session class and a role miss would be reported as a lost login rather than as a permission problem (R-26, K-34).

**Status.** `AdminReviewCard` has no approval state without a durable store and `PublishControl` has no source at all (A.12; WCM §23), so neither may be rendered as a lane before the store exists. Where approval state lives is **K-09**; annotations are **K-47**; whether a delegated admin performs the publish act at all is **K-55**.

## F.13 Project Workspace

**v1 is a projection plus launchers.** Slice one discovers workstream state, renders it, derives readiness, deep-links into the work and writes nothing (WSP:415-430,562-589). ## F.14 Worker observability and branch lifecycle

**The defect.** A build that will never land must be knowable from Forge within one poll cycle. Refusal is a result, not silence. At `824c4d58` worker validation refusals and a missing result stop before the persist step (`824c4d58:.github/workflows/quest_studio.yml:59-77,106`), and a run cancelled by the concurrency rule (`:26-28`) also persists nothing, so the result read returns not-found (`824c4d58:forge/src/studio/repository.mjs:115-117`) and the UI ends in "Build still running" after thirty two-second polls (`824c4d58:forge/src/studio/ui.mjs:446-449`), indistinguishable from a slow queue. Forge stores no workflow-run identifier and the client has no Actions-run read (`824c4d58:forge/src/github.mjs:131-148`). RB §11 expects `Repository unavailable`, `Build failed` and `Build blocked` to be distinguishable (RB:271-280), and the Tier C safety contract forbids letting machine state read as something it is not.

| Outcome today | What Forge sees | What it must become |
|---|---|---|
| worker validation refusal | no result document; the read returns not-found | a named refusal within one poll cycle |
| compiler ran and failed | a result document with a failed status, then a red run | unchanged; this one already works |
| result missing after the compile step | no result document | a named failure, not silence |
| run cancelled by the concurrency rule | no result document; the newer poll simply supersedes | the older request is named as cancelled |
| slow queue | no result document yet | a check-later state with backoff, distinguishable from all of the above |

**Two mechanisms, one to be chosen.** Either the worker persists a refusal envelope with a distinct status and code before exiting, which costs nothing on the credential side, or Forge gains an Actions-run read, which requires an additional permission on the token. Both are compatible with the F.6 envelope. Which one ships is **K-38**, and it becomes a director question rather than an engineering one if the token widens.

**Independent of that choice:** a visible check-later state with exponential poll backoff replaces the fixed thirty polls, so the operator is told to come back rather than watching an indefinite running state; and a cancelled run is named as cancelled rather than left as silence.

**Branch lifecycle.** Each request creates one permanent branch with no cleanup, re-compiling the same identifier overwrites the source file through a sha-aware write (`824c4d58:forge/src/github.mjs:111-128`) and removes the previous build directory (`824c4d58:.github/workflows/quest_studio.yml:120`), and identifiers are derived from the device clock (`824c4d58:forge/src/studio/ui.mjs:62-64`), so two devices cannot share a draft. Polling spends GitHub API quota rather than game budget (R-17). A retention and cleanup rule for the branch namespace, and how conflicts are handled, is **K-37**; it belongs in the development workflow document, not in Forge code.

## F.15 GitHub bridge and credential model

**Shape.** One transport (`github.mjs`), one closed typed operation list above it (F.6), one credential. Reads need no credential on a public repository and writes refuse without one (`github.mjs:22-27,50-57`), which is the property the review-queue recommendation depends on (F.12). The PAT lives under the key shared with Builder (`compat.mjs:5`) and its shape is unchanged while Builder stays installed.

**What the Studio seam widens.** The seam needs branch creation and workflow dispatch in addition to contents write (A.11 consequence 2), and F.14's second mechanism would add an Actions-run read. That is a real widening of the token on the operator's phone and it is **K-15**, with the trigger and branch architecture as **K-26**.

**Two consequences worth stating plainly.** First, attribution: the actor recorded by any repository write is the token, not the person, and one shared key serves both tools, so a review decision's actor is self-asserted rather than authenticated. A surface that shows "who decided" must say which of those it means. Second, and this is a rule rather than a consequence: **the absence of a PAT never implies that live game work is unavailable.** They are separate credentials on separate origins with separate failure modes; the game session is a same-origin cookie session the transport never touches directly, and the GitHub token is a repository credential. A UI that greys out live work because sync is unconfigured, or that reports a failed repository commit as a failed game write, breaks the single most important distinction in the tool. The sync state in F.8 exists precisely so those two claims stay separate.

**One more separation worth naming.** Repository reads, repository writes and game work fail independently and must be reported independently. A failed listing of work packages is a repository read failure and is retry-safe; a failed bundle commit is a repository write failure and is retry-safe on demand but never automatically, because an automatic retry races the repository's own automation (R-07); a refused game mutation is neither, and the only path out of an ambiguous one is reconciliation. The three share no control, no colour and no wording, and "Try again" exists only on the first two.

**Unchanged.** Game cookies and session material never enter repository artefacts or logs; the static forbidden-string test in `forge/test/auth.test.mjs` is the mechanical guard and it is preserved.

## F.16 Release, pin, install and the bundle budget
